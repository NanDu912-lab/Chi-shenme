# JTBD｜工作日下班后晚餐“吃什么”决策任务分析
> 用户诉求：<br>
> **当**工作日结束下班，身心疲惫、认知资源消耗殆尽，还没有确定晚餐方案；<br>
> **我希望**摆脱晚餐选择带来的精神纠结与决策内耗；<br>
> **从而**得到一个可接受、适配自己当下身心状态的一餐。

> 用户“雇佣”产品的目的：不是发掘大量美食，而是**结束选择带来的痛苦**。

## 1. 用户情境与任务三层拆解
### 触发情境
- 时间：工作日傍晚下班路上、刚到家
- 用户状态：精力不足、决策力耗尽，处于饥饿状态，未提前规划晚餐；预算、胃口、是否做饭均为动态变化
- 使用范围：以单人就餐为主；部分场景为室友、伴侣共同多人决策

### 三层任务拆解
1. **功能任务**
快速确定可行的晚餐方案（外卖 / 堂食 / 简易居家做饭），能够顺利吃上饭。
2. **情感任务（最高优先级）**
停止反复挑选造成的精神内耗；尽量避免吃到难吃的食物；部分用户希望借晚餐犒劳辛苦一天的自己；尽可能不消耗仅剩的脑力。
3. **社会任务（次要独立任务）**
多人就餐场景，需要兼顾多个人口味，达成就餐共识。

## 2. 用户现有替代方案与痛点
在没有本工具的情况下，用户当下会采用的解决方式：刷外卖App、询问身边朋友、翻找冰箱存货、吃泡面、选择常吃老店、浏览美食种草内容、随机抓阄。

现存痛点：
1. 外卖App选项过多，越刷越纠结；
2. 咨询他人常常得到“随便”这类无效回复；
3. 长期吃固定店铺容易吃腻；
4. 网络种草美食存在距离、价格不匹配的问题，增加筛选成本。

## 3. 四力模型：用户切换新工具的决策逻辑
- **推力（现状痛苦）**：下班之后做餐饮选择会消耗仅剩精力，容易陷入选择瘫痪；现有方案要么选项过载，要么结果不尽人意。
- **拉力（新产品吸引力）**：无需自己权衡对比，工具直接给出可接受候选，快速结束纠结。
- **阻力‑习惯**：刷外卖、询问他人是长期使用的行为习惯，用户会本能打开已有App。
- **阻力‑焦虑**：担心工具推荐不合胃口，发生踩雷；对算法给出的结果不信任。

> 用户发生切换的条件：推力 + 拉力 ＞ 习惯 + 焦虑

## 4. 核心假设（待验证，并非既定事实）
1. 假设：多数工作日下班用户处于决策疲劳，希望降低晚餐选择的思考成本。
    - 反例：有一部分用户享受慢慢刷外卖挑选美食的过程。
    - 验证方式：用户访谈提问：“下班挑选晚餐的时候，你是享受挑选过程，还是觉得这件事很耗费精力？”
2. 假设：用户不需要“最好吃的晚餐”，只需要一个可以接受、无需继续思考的选项。

## 5. 任务映射产品功能（MVP）
> 产品定位：**晚餐拍板决策工具，不是美食库、不是外卖平台**
> 核心原则：少选项、低思考、快速拍板，拒绝信息流，拒绝无限刷取内容。

### P0｜必须上线（服务核心JTBD任务）
1. **一键拍板（核心功能）**
点击帮我决定，一次性返回2‑3个候选方案（外卖/简易家常菜/堂食混合输出）；展示信息极简，不堆砌大图、大量评价内容。
2. **轻量筛选器（固定4项，不再新增）**
预算档位；就餐方式；忌口标签；就餐人数；全部默认放开，不强制填写，避免增加决策负担。
3. **有限换一批机制**
最多允许换2轮；次数耗尽给出提示：别纠结，就从上面选一个；通过限制刷新对抗决策瘫痪。
4. **确认选择**
选中方案后记录本次选择，沉淀用户偏好；可选择性跳转外卖链接，不作为强制流程。
5. **一键踩雷标记**
标记“不想再看到该选项”，无需填写理由，后续降低该选项的推荐优先级。

### P1｜迭代版本
1. 情绪模式切换：糊弄一顿 / 犒劳自己模式
2. 极简历史记录，仅展示最近5条选择记录
3. 多人协作模式：分享码实现共同投票（属于独立任务，不为单人主流场景做妥协）
4. 用户自建备选池，支持录入常吃店铺、拿手菜谱

### ❌ MVP禁止实现（防止偏离JTBD核心任务）
- 不做美食图文社区、种草笔记、美食攻略
- 不爬虫搭建海量餐厅、菜品库
- 不做排行榜、热度排序、大量评价展示
- 不做复杂菜系、精细热量筛选
- 不做完整外卖下单、配送跟踪流程
- 不做饮食数据分析、长期统计报告
- 不接入商家广告与商业引流

## 6. JTBD任务完成度验证指标
> 产品理想状态：用户停留时间越短越好，越快完成决策越好。
1. 打开工具到选定方案平均耗时（目标30秒以内）
2. 用户换一批次数分布；目标：大部分用户第一轮即可选定方案
3. “不想再看到”点击占比，衡量推荐匹配程度
4. 回访率：当再次纠结晚餐吃什么时，用户是否会再次打开工具

## 7. 产品风险与边界
1. **功能堆砌风险**：产品很容易逐步演变为普通美食App，反而加重选择内耗，背离原始任务。
2. **推荐不准风险**：多次推荐踩雷，用户会直接“解雇”该工具，不再使用。
3. **口味动态变化风险**：用户每日胃口会发生波动，静态标签无法做到100%精准命中。
4. **业务边界**：本产品解决的是**决策纠结问题**，而非“帮用户找到全世界最好吃的饭”。
